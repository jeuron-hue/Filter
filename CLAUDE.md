# CLAUDE.md: filter

## What this is
filter sorts the photos and videos on Gary's Pixel 9 Pro XL into folders by what is in them. It is a PWA installed from GitHub Pages (jeuron-hue/filter, public), like retouch. Private working tool, not a portfolio piece. Agreed 29/10/26 as a separate app from retouch: retouch edits one picture, filter organises many.

## Hard rule: photos never leave the phone
- All recognition runs on the phone, in the browser, with vendored models. No uploads, no cloud APIs, no analytics, no telemetry.
- Enforced, not promised: a Content-Security-Policy meta tag with connect-src 'self', and a static test that fails on any other origin in the source.
- No libraries, models or fonts from CDNs. Everything is vendored so the app works offline after first load.
- No real photos of people in the repo. Test pictures that need real content live in reference/test-images/ (gitignored); tests that need them skip cleanly when it is absent.

## Hard rule: never lose a file
Gary keeps no backup (no Google Photos backup). On Android a web app cannot rename or move a file; a move is a copy and then a delete. So:
- A move is always: copy, read the copy back and check it is byte-identical to the original (size and SHA-256), and only then delete the original. Any mismatch stops the run and keeps both.
- Review mode: Gary chooses copy or move when he confirms; copy is the default and leaves the original untouched.
- Auto mode: every file sorted is moved, the safe way above (Gary's rule, 29/10/26), so nothing is lost and nothing is left doubled up.
- Every run writes a log (what went where, with hashes) to filter-logs/ in the picked folder, as a new file that never replaces another, so the last run can be undone the same safe way.
- These rules hold in both run modes (below). In Auto mode, a picture filter is unsure about stays where it is.

## Run modes (Gary picks per run)
- Review: filter shows its plan first, a grid per proposed folder; tap a picture to send it elsewhere. Nothing is copied, moved or deleted until Gary confirms.
- Auto: filter sorts straight away, moving each file by verified copy then delete, and shows what it did afterwards, with undo for the run.

## Recognition modes (Gary picks per run)
- By description: folders named by what is in them. A fixed list filter knows (people, pets, food, screenshots, documents, scenery, other), plus a few of Gary's own, typed and edited by him (say "receipts" or "hawker food"). See Recognition under Architecture.
- By example: Gary makes each folder himself, as a subfolder of filter-examples/ inside the picked folder, and places 3 example pictures and 3 example videos in it. A picture is compared with the example pictures, a video with the example videos; each goes to the closest folder, or to "unsure" when nothing is close enough or two folders are too close to call. Copies go to a subfolder of the picked folder with the example folder's name, as in F1. See F2 under Phases.

## Architecture
- Vanilla JS and CSS, no framework, no build step, no server. filter.html holds the whole app; extra files only as a PWA needs them (manifest.webmanifest, sw.js, icons/, vendor/, index.html redirect stub). Test tooling sits beside it.
- Folder access: the File System Access API (showDirectoryPicker), available in Chrome on Android since Chrome 132 (01/25). Very large folders (all of DCIM) can stall it, so filter reads in batches and can start from a subfolder.
  - Permission is lost at every restart (F0). filter keeps the folder handle in IndexedDB and, on start, shows one "Allow access" button where the folder buttons are, so a single tap brings the folder back; the status strip says plainly when access needs re-granting.
  - Looking a file up by name in a big folder costs seconds (F0: 4.2 s in DCIM/Camera, 8.5 ms in a small folder). filter works from the handles one listing returns, keeps each folder's names in memory, and never looks files up one by one in a big folder. F4 must cut the per-file lookups of the safe move (open the original from the listing's handle, test whether deleting through the file's own handle avoids the lookup, check that originals are gone with one fresh listing per batch); at three lookups a moved file costs about 12 s, about 3.5 h per 1000.
- Running time: Android freezes a web app soon after it leaves the screen, and a web app cannot work in the background (Gary asked, 30/10/26), so a run only goes on while filter is shown. Since v0.3.4 filter keeps the screen on while it works (Screen Wake Lock, taken again when filter comes back on screen; a refusal, say on low battery, does not stop the run), so the phone can be put down for a long run. A video being read when filter left the screen is read again once it is back (up to 3 tries in all); photos and copies simply wait, and an interrupted copy is never counted as done.
- Recognition: MediaPipe Tasks Vision, the same pinned version as retouch (0.10.35, not 1.x, which logs usage to Google).
  - By description, fixed list: an image classifier (EfficientNet-Lite0), a face detector (BlazeFace short range, run on the whole photo and on four overlapping quarters so smaller faces are found) and an object detector (EfficientDet-Lite0 int8, the 80 COCO objects: finds whole people, cats, dogs and common foods), plus plain rules, in order: screenshots (by name, or a screen-shaped PNG with no camera data); people (a face at 0.75, or 0.85 if seen only in a quarter; or two person boxes, or one covering 8 % of the photo at 0.65); documents (mostly text: bright, little colour, dark strokes); a cat, dog or food box at 0.6 covering 3 %; then the folder whose classifier labels add up highest among its top 10 (pets, food, documents, scenery) if the sum reaches 0.25, else other. Food labels are dishes only (no "restaurant", which is a room). Each photo is decoded once at 1280 px, ahead of time while the models work on the one before, and the first look uses a 512 px copy. Photos not decided as people or screenshots on the first look get a closer look: the object detector searches the 1280 px decode in nine overlapping parts (3 x 3, each 45 % of the photo); every box is put back on the whole photo and boxes of one label that overlap (intersection over union 0.4, or 70 % of one inside the other) count once; the closer look adds only person boxes of at most 12 % of the photo (people far away; a big "person" in one part is a piece of something close up), then the same rules decide again. A person box filling at least 90 % of both the width and the height, with no face, is a close-up of part of a body: it does not count as a person, and goes to other (Gary, 30/10/26: body-part close-ups are not people), unless the classifier's labels for clothes worn on the body (suit, ties, jersey, coats, gowns and the like, in CLOTHES; not jeans, underwear, swimwear or shoes) add up to 0.25 with the box at 0.65: then it is a tight portrait and counts. After a close-up the closer look is skipped. Faces at classroom distance are below what the short-range face detector sees at any size, so people in rooms come from the object detector. Each threshold is one named value in RULES; the label groups are checked against the labels inside the models.
  - By description, typed: needs a model that reads both words and pictures into the same numbers (a CLIP-style model), so a typed folder name can be compared with a picture. MediaPipe has none, so this is a second runtime (about 100 MB more to download) and slower on the phone. Which model, under which licence and at what size, is settled and written here before F5 starts; its licence must allow this use.
  - By example: an image embedder (a model that turns a picture into a list of numbers, where similar pictures get similar numbers): MediaPipe ImageEmbedder with MobileNet-V3 large (float32, 10.9 MB, 1280 numbers per picture, Apache-2.0; Gary's choice over small, 4.1 MB, 30/10/26: sharper at close folders, and decoding sets the pace anyway). Only the embedder loads for a run by example; F1's three models and the closer look are not used. Each folder's example pictures (and, from F3, its 3 example videos) become its reference points. A photo's score for a folder is its cosine similarity to that folder's closest example (1 is the same direction); the best folder wins if it scores at least minSim and beats the runner-up folder by at least minGap, else the photo is unsure. Both are named values in RULES: minSim 0.32 since v0.2.2 (0.50 in v0.2.0, 0.35 in v0.2.1; set from Gary's first three runs, see F2), minGap 0.05. The score tracks the shoot as much as the kind of picture, so examples from many different days work better than a lower bar.
  - Speed: decoding the photo, not the model, set the pace in F0 (380 ms to decode, 50 to 80 ms to classify). The small preview inside each JPEG made the first look fast (0.2 s per photo) but is too small for people at a distance; since v0.1.3 each photo is decoded once at 1280 px, ahead of time, instead. The CPU delegate stays unless the GPU proves faster on whole runs.
  - Videos: three frames sampled (10 %, 50 %, 90 % through), each decoded like a photo (1280 px, with a 512 px copy). By description, each frame goes through the same models and rules; a frame that sees nothing clear (other) does not vote, and the folder seen in the most of the remaining frames wins, so one frame of scenery and two of nothing is scenery (since v0.3.2); a tie between two folders, or nothing clear in any frame, leaves the video in other. By example, the three frames' numbers are averaged and compared with the example videos' only, against bars of their own in RULES (minSimVideo, minGapVideo; 0.32 and 0.05 to start, the photos' values). One video is opened at a time, as a phone may have only a few video decoders. On the phone a seek can report done before the new frame is on show, so the same picture was taken for two or three frames (v0.3.0, v0.3.1); since v0.3.3 the video sits on the page (2 px, nearly clear) and filter waits until the browser shows a frame within 0.25 s of the time asked for (requestVideoFrameCallback, up to 3 s); a frame it could not confirm is still used and marked "frame not confirmed" in the run details. A file over 64 MB (a video) is hashed in 4 MB pieces by a plain JavaScript SHA-256 in CORE, as the browser's own needs the whole file in memory; it gives the same hash.
- Models come from Google's model store. Claude's cloud session reached it on 29/10/26 and fetched EfficientNet-Lite0 directly; the rig shell cannot reach it, so there Gary downloads each model and Claude vendors it. Either way each model is vendored with its sha256, version and licence in the filter.html build notes.

## Design
filter's UI is not decided yet (Gary, 30/10/26): the functions are built first and the UI is redesigned after. Until Gary decides, the build keeps retouch's darkroom style as a stand-in (filter_checks.cjs holds the tokens below while it does); it is not a decision. The parts of retouch's CLAUDE.md Design section in use:
- Dark only. Neutral near-black surround so the pictures are judged fairly; the pictures are the brightest thing on screen. No light theme.
- Tokens (CSS custom properties at the top of filter.html), the same values as retouch: stage #0B0B0B, chrome #141312, raised #1D1B19, pressed #2E2B27, lines #2C2925 / #3A3631, ink #EEE8DE, muted #A59E92, faint #8A8377. One accent, the amber safelight #F2A33A (text on it #1B1205). Pass #7DBE8A, watch #E0A84A, fail #E57360.
- Type: Barlow Semi Condensed 400/600 for labels and buttons (labels in spaced capitals), IBM Plex Mono 400/500 for numbers and counts, vendored in vendor/fonts/ (copied from retouch).
- Motifs: film-edge labels in amber mono (counts, folder names, the run date), sprocket holes along the bottom bar, crop-mark corners on the empty screen and the icon. filter gets its own icon in the same style.
- Phone first: portrait, one-handed, tap targets at least 44 px.
- Uncluttered: status in a thin strip at the top; short captions only where they apply.
- The review screen is the heart of Review mode: a grid per proposed folder, counts per folder, tap a picture to send it elsewhere, one amber confirm. Press and hold a picture to pick several (Gary, 30/10/26): taps then pick more or leave one out, picked tiles get a thick amber frame and a tick, the bar shows Cancel and Send to, and Send to puts them all in one folder. Auto mode ends on the same screen, showing what was done, with undo.

## Phases
Each phase on its own branch, all suites green, Gary merges, tests on the Pixel and confirms before the next.
- F0: probe on the Pixel. Pick DCIM/Camera; read a batch of 500; create a subfolder; copy, verify and delete a test file; reopen the folder after closing the app (does Chrome keep the permission?); time recognition per photo. The answers are written here before F1 starts. Done 30/10/26 with the probe (filter.html v0.0.2) on the Pixel 9 Pro XL, Android 17, Chrome 155, installed app. (1) Reading: DCIM/Camera (1861 entries) opens with no stall; about 6 s before the first entry, then the whole folder by 6.6 s. Reading a file (getFile) costs 80 to 115 ms. (2) The safe move works on the phone: the copy was byte-identical (size and SHA-256), the original deleted and gone; a forced bad copy stopped before any delete and kept the original. The cost is in name lookups, not data: finding a file by name took 4.2 s in DCIM/Camera against 8.5 ms in a small folder, so deleting from Camera took 4.1 s and a 3 MB move 13.8 s in all, of which reading, writing and hashing the bytes took about 1 s. Creating a file or folder in Camera took 16 to 20 s. (3) Folder permission does not survive a restart ("prompt" on all four reopenings); the stored handle does, and one tap on Chrome's permission prompt re-grants it (2.7 s), with no picker. (4) Recognition: decoding a 12.5 MP photo to 512 px takes about 380 ms; the classifier then takes 77 ms on the CPU, 53 ms on the GPU (whose first call takes 0.8 s). About 7.5 min per 1000 photos either way: decoding is the bottleneck. ImageNet labels fit poorly (top scores 0.06 to 0.18 on 3 of 5 photos), which is why the fixed list comes from rules over them plus the face detector.

## Versions and changes
The same rule runs in every app repo (retouch, filter, travelboard, icantell), agreed with Gary 30/10/26. The full method is in the version-release skill.
- Numbers run x.y.z. Patch (z): a fix or retuning, nothing new to learn. Minor (y): something new Gary can do, a finished phase, or a visible redesign; the patch goes back to 0. Major (x): 1.0.0 only when Gary declares the app finished after real use; after that x moves only when something old stops working (saved data, a file format). Until then the app stays on 0.x.
- One version per release. A release is any change to the app that reaches main. Docs-only and test-only work carries no bump and is listed in the next version's entry. A work-in-progress checkpoint does not bump the version; the bump goes in the commit that completes the release.
- The bump changes APP_VERSION in filter.html (the header line and the constant) and CACHE_VERSION in sw.js together, in the release commit, and the commit subject ends with (vX.Y.Z).
- CHANGELOG.md gets the version's entry in the same commit, at the top (newest first): a heading `## vX.Y.Z, dd/mm/yy HHMM hrs`, optionally followed by `, <phase>`, giving the date and time the release commit is made, in Singapore time; then one or more `- ` lines saying what changed, in plain words. Reasons and phone results stay in this file under Phases. A released entry is changed only to correct a fact. In filter each heading ends with the phase (`, F<n>`); the lines cover what Gary sees, rules and their values (old to new), models added, what is written to the phone, and new kinds of test, with the reason in a few words; the full why and the Pixel run results stay in this file. When Gary closes a phase, its last version's entry adds "F<n> closed by Gary at this version."
- filter_checks.cjs fails if a heading lacks the version, date or time, the newest entry is not the current version, versions or times are out of order, or an entry has no change line.
- Each release is built on its own branch and merged by Gary through a pull request; the branch is deleted after the merge. Once merged, the release is tagged vX.Y.Z on its commit in main; a session that finds a merged release without a tag adds it.

## Testing
- filter_checks.cjs (static): CSP, no external origins, allowed files only, vendored versions, hashes and licences recorded, copies only, filter-examples/ never written, CHANGELOG.md in step with APP_VERSION (see Versions and changes).
- filter_behave.cjs (Chromium via Playwright): synthetic fixtures built in the test (coloured shapes, text images, screen-sized PNGs, short WebM clips recorded from a canvas in three flat thirds, so the frames at 10, 50 and 90 % fall one in each), a fake folder tree in place of the real picker, numeric checks on where each file lands, and on copy, verify, delete and undo, including a forced mismatch that must stop the run with both files kept. - Everything green before any commit.
